## Warning 级违规

### [R-NAME-01] `addons/skill_editor/dock/TimelineView.gd` 未声明 class_name 但文件名走 PascalCase

- **文件**：`addons/skill_editor/dock/TimelineView.gd:1`
- **现象**：脚本以 `extends Control` 开头，未声明 `class_name`；文件名是 `TimelineView.gd`（PascalCase）。
- **规则匹配**：R-NAME-01 第 4 类「其他纯驱动/工具脚本（不声明 class_name 也非 Autoload）：走 snake_case.gd」。
- **不构成 Error 的理由**：本文件是 `SkillEditorDock.tscn` 内部 Control 节点的脚本，命名直观对应节点名"TimelineView"；同时未来很可能补 class_name 用于子类化。
- **整改建议**：推荐在文件头加 `class_name TimelineView`（最低成本方案，文件名无需改），即可满足 R-NAME-01 第 1 类。这样还能让 Inspector 显式展示类型，对编辑器调试更友好。
- **附注**：同目录 `plugin.gd` 也无 class_name，但 Godot EditorPlugin 入口文件按惯例就叫 `plugin.gd`，且 `plugin.cfg` 通过 `script="plugin.gd"` 硬绑定，属于框架约定例外，不报。

### [R-LOG-01] `SkillEditorDock.gd` 6 处裸 `print(...)` 未在文件头声明编辑器例外

- **文件**：`addons/skill_editor/dock/SkillEditorDock.gd`
- **命中行**：
  - L186：`print("[SkillEditor] preview started")`
  - L192：`print("[SkillEditor] preview paused")`
  - L198：`print("[SkillEditor] preview reset")`
  - L209：`print("[SkillEditor preview] @%.2fs anim '%s'" % [...])`
  - L212：`print("[SkillEditor preview] @%.2fs event kind=%s payload=%s" % [...])`
  - L216：`print("[SkillEditor] preview finished")`
- **规则匹配**：R-LOG-01「业务代码使用 GameLogger.info/warn/error；禁止裸 print()」。
- **现状对比**：同目录 `plugin.gd` 已在文件头第 11–12 行加了显式注释：
  > "R-LOG-01 例外说明：本目录下的 @tool 脚本运行在编辑器进程，无法访问 GameLogger（因依赖运行时 Autoload）。改用原生 push_error / push_warning。"
  
  `plugin.gd:27` 用 `push_error`，与该例外声明一致。但 `SkillEditorDock.gd` 没有同样的例外声明，且用的是 `print`（而非 `plugin.gd` 声明允许的 `push_error/push_warning`）。
- **不构成 Error 的理由**：R-LOG-01 本身严重级是 Warning；且这些 print 都是 @tool 编辑器进程下的预览日志，不会进入运行时输出。
- **整改建议**（二选一）：
  1. **首选**：在 `SkillEditorDock.gd` 文件头补充与 `plugin.gd` 一致的 R-LOG-01 例外说明注释，并把 6 处 `print()` 全部改为 `print_rich()`（带颜色更醒目）或保留 `print()`。例外注释建议如下：
     ```gdscript
     ## R-LOG-01 例外说明：本脚本带 @tool 标注，运行在编辑器进程，无法访问 GameLogger
     ## （GameLogger → EventBus 等运行时 Autoload）。预览日志使用原生 print()。
     ```
  2. **次选**：为编辑器进程做一个小工具 `EditorLogger.gd`（不依赖任何运行时 Autoload），让所有 @tool 文件都通过它输出，统一编辑器日志格式。规模太大不必为 M7 做。

### [R-DATA-02] `SkillEditorDock.gd:342` SpinBox `time_spin.max_value = 60.0` 玩法语义可调

- **文件**：`addons/skill_editor/dock/SkillEditorDock.gd:342`
- **命中内容**：`time_spin.max_value = 60.0`（关键帧 time SpinBox 的最大可输入值）
- **规则匹配**：R-DATA-02「未来很可能要调的值」候选；同时该值意味着"单条 SkillTimeline 的关键帧时间最大 60 秒"，已经摸到玩法（技能时长上限）边界。
- **不构成 Error 的理由**：R-DATA-02 例外条款明列「Editor 工具/插件内部 UI 布局参数（不影响 runtime 玩法）」。该值只影响编辑器 SpinBox 的输入上限，runtime 时若 .tres 中的 time > 60 仍可正常运行（运行时不读这个 SpinBox）。
- **整改建议**：
  - **保守方案**：保留现状，但顶上加注释说明"60s 是编辑器 UI 输入上限，不是运行时约束"。
  - **进阶方案**：未来若引入 `Data/Config/SkillEditorConfig.tres`（编辑器自身配置），把这种"编辑器输入上限"统一收纳。当前 M7 没必要单独加。
- **附注**：`TimelineView.gd` 顶部 13 个视觉常量（ROW_HEIGHT/RULER_HEIGHT/COLOR_*/KEYFRAME_RADIUS）已被 R-DATA-02 例外条款明确豁免（编辑器 UI 布局 + 颜色）；本扫描通过。

## 给主 agent 的建议

### 1. 是否阻塞 M7 验收
**不阻塞**。M7.1–M7.6 在所有 6 条 Error 级规则上完全合规；3 条 Warning 都集中在编辑器插件代码（`addons/skill_editor/`），不影响运行时正确性，也不影响数据驱动设计的核心价值。验收建议直接通过。

### 2. ⚠ 数据隐患（非规则违规但建议关注）：3 个 Ability_*.tres 中 ability_id 重复

- `Ability_EnemyBasicAttack.tres:7` `ability_id = &"enemy_basic_attack"`
- `Ability_BossBasicAttack.tres:7` `ability_id = &"enemy_basic_attack"` ← **同名！**
- `Ability_PlayerBasicAttack.tres:7` `ability_id = &"basic_attack"`

如果一个 ASC 同时被 grant 这两份 .tres，会发生 id 冲突（取决于 ASC 内部 Dictionary 实现，后写覆盖前写）。当前 EnemyCharacter / BossCharacter 应该是分别只 grant 自己的那一份所以未暴露问题。**建议**：把 `Ability_BossBasicAttack.tres` 的 `ability_id` 改为 `&"boss_basic_attack"`，与 `timeline_id` 对齐；同时给 BossCharacter 的 `enemy_id` 槽位绑同名。这条不算规则违规（R-NAME-01 不约束资源内字段值），但属于 Boss 与小怪的"逻辑分离"原则未走通的小漏洞。

### 3. 高频违规的根因：编辑器进程的日志/数据规范没标准化

本轮 3 条 Warning 全部来自 `addons/skill_editor/`，说明项目目前**只为 runtime 制定了 R-LOG-01 / R-DATA-02 落地实践**，对 @tool 编辑器进程暂未提供"对应版本"的工具或例外约定。建议在 M8 前后做一件小事：

- **新增 `addons/skill_editor/EditorLog.gd`**（10 行薄封装），把 print_rich + 颜色 + channel "[SkillEditor]" 统一封装；把 `SkillEditorDock.gd` 6 处 print 改用它。
- **写入项目级编辑器约定**：在 `Plans/全局规则.md` R-LOG-01 下追加一句"@tool 脚本可使用 push_error/push_warning（无法 GameLogger）；项目级建议每个插件提供 `EditorLog.gd` 封装"。
- 这样未来其他 @tool 工具（M8+ 数据表编辑器、M9 关卡工具）会有统一基线。

### 4. 是否要写入开发模板/脚手架

M7 已经把"数据驱动"练得非常扎实（SkillEventKind / SkillTrack.KIND_* / EventTrackHandler.KEY_* / META_* 4 套常量层），这套写法非常值得在 M8 起的新模块（Buff 系统、状态机配置等）继续沿用。建议把这种"为枚举/字符串字面量提供专用 const 类"的模式，写入 `Plans/开发计划.md` 的"通用模式"或"M8 启动提示"区块作为推荐。
