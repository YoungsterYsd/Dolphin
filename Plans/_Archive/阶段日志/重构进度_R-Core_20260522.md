## 三、关键踩坑：Autoload 与 class_name 同名冲突 ⚠️

### 现象
最初给 ConfigCenter 加上 `class_name ConfigCenter` 后，全项目改 `ConfigCenter.get_xxx()` 直访引发**Parse Error**：

```
Cannot call non-static function "get_character_def()" on the class "ConfigCenter" directly.
Make an instance instead.
```

### 根因
Godot 的 Autoload 机制本身就把节点名注册为**全局符号**（指向运行时实例）。给同名 .gd 加 `class_name` 后：
- 同一个标识符 `ConfigCenter` 既是"类名"（静态调用）又是"Autoload 实例引用"（成员调用）
- GDScript 解析器**优先走类静态语义**，导致所有非 static 方法调用全部解析失败

### 解法
**Autoload 节点的 .gd 文件不要加 class_name**，业务侧仍直接写 `ConfigCenter.get_xxx()`，GDScript 自动解析为 Autoload 实例方法调用。

### 教训（沉淀到 R-CODE / R-ARCH 范畴）
- **Autoload 全局符号即实例引用，不需要也不应当有 class_name**
- 如果某 Resource / 工具类（非 Autoload）需要被业务侧用类名引用，才加 class_name
- 如果两者都需要（既要 class_name 又要 Autoload）：必须**类名与 Autoload 注册名不同**（如 `class_name ConfigCenterClass` + Autoload 注册为 `ConfigCenter`），但实操上不建议——直接用 Autoload 即可

## 五、新沉淀的原则（建议追加到全局规则）

### 候选 R-ARCH-03（Autoload 使用约定）
- **Autoload 节点的 .gd 文件禁止加 `class_name`**
- 业务侧统一通过 Autoload 名（全局符号）直接调用，例：`ConfigCenter.get_xxx()` / `EventBus.signal_name.emit(...)` / `GameInstance.skill_timeline_player.play(...)`
- 禁止 `get_tree().root.get_node_or_null(^"ConfigCenter")` 这种"动态查 Autoload"模式（除非确实存在静态识别滞后问题，且必须在注释里说明）

### 完善 R-CODE-01（崩溃式失败延伸）
- 启动期必备资源（如 GameplayTagRegistry / CharacterInstanceTable / 各种 Config）缺失 → assert 崩
- 静态可知的信号 / 方法 → 禁用 `has_signal` / `has_method` 防御反射
- 跨文件的 Autoload 互引用：直接用 Autoload 名，不要走"运行时 get_node_or_null"
