## 二、重构 Roadmap

下面按"风险/收益/依赖"排序成**6 个 Phase**，每个 Phase 都设计为**可独立交付** + **R-VERIFY-01 自测可通过**。

### Phase 1 · 高 ROI 跨模块基建（2-3 天，最优先）

**目标**：把 Top 6 共性问题中的 G1 / G2 / G3 / G5 一次性清掉，为后续 Phase 扫清地雷。

| 步骤 | 操作 | 影响面 |
|---|---|---|
| 1.1 | ConfigCenter 加 `class_name ConfigCenter`；项目设置保持 Autoload | 仅改 ConfigCenter.gd 一行 |
| 1.2 | 全项目搜 `get_tree().root.get_node_or_null(^"ConfigCenter")` + `cfg.call(&"...")` 模式，批量替换为 `ConfigCenter.xxx()` | 15+ 处 |
| 1.3 | 删 ConfigCenter 内 8 处 `XxxConfig.new()` 兜底，改 assert | ConfigCenter.gd |
| 1.4 | grep `EventBus.has_signal(...)` / `asc.has_method(...)` 等防御，批量删除（保留运行时数据缺失场景） | 30+ 处 |
| 1.5 | grep `for child in get_children(): if child is X` 等内联查找，改 `NodeFinder.find_first_child_of_type` | 8+ 处 |
| 1.6 | grep `asc.call(&"_detach_active"` 替换为 `asc.remove_effects_with_granted_tag` | DamagePipeline / CombatStateService |
| 1.7 | 自测：lint + restart + run_project 端到端 | R-VERIFY-01 |

**预期收益**：30+ 文件减少冗余代码，6 大共性中 4 个直接消除。

### Phase 2 · GAS 巨型类拆分（3-4 天）

**目标**：拆 `AbilitySystemComponent.gd`（631 行）+ 修 DamagePipeline 残留问题。

| 步骤 | 操作 |
|---|---|
| 2.1 | ASC 拆为 4 部分：`ASCAbilityRegistry`（grant/revoke/try_activate）+ `ASCEffectRuntime`（apply_effect_spec/_attach/_detach）+ `ASCAttributeBootstrap`（bootstrap_from_entity/ensure_sets，本次重构已写入）+ `AbilitySystemComponent`（聚合容器） |
| 2.2 | DamagePipeline 重构：`_get_asc` 改 BaseCharacter 强类型；`_remove_perfect_block_buff` 改 `remove_effects_with_granted_tag` |
| 2.3 | 4 个魔数（DEFENSE_K=100 / BLOCK_REDUCTION=0.4 等）迁 `Data/Config/CombatBalanceConfig.tres` |
| 2.4 | AttributeSet 反射钩子 `_pre_change_*` 改注册表（PrimaryAttributeSet 4 个 clamp01 一并改） |
| 2.5 | Ability_TimelineDriven 6 处 ConfigCenter/GameInstance 兜底改 assert |
| 2.6 | 自测 R-VERIFY-01 |

**风险**：动 ASC 接口可能影响 BlockComponent / EnergyComponent / HitDamageResolver 等下游；建议先做接口兼容层，再分步迁移。

## 三、Phase 之间的依赖关系

```
Phase 1（基建）
    ↓ 必须先做（消除全局共性问题，让后续 Phase 改造面减小 30%）
    ↓
Phase 2（GAS 拆分）─────────┐
                            ↓
Phase 3（UI 拆分）───────── Phase 4（业务收口）
                            ↑
                    （4 依赖 2 的 ASC 接口稳定）
                            ↓
                    Phase 5（长尾优化）
                            ↓
                    Phase 6（长期演进 backlog）
```

**关键约束**：
- Phase 1 必须**最先做**：它是后续所有改造的基础（ConfigCenter 强类型、NodeFinder 收口、删兜底）。
- Phase 2 与 Phase 3 可**并行**（两条不交叉的代码线）。
- Phase 4 依赖 Phase 2 的 ASC 接口稳定（拆出 `ASCAbilityRegistry` 等之后，QuestRewardDispatcher 才好接）。
- Phase 5 在 Phase 1-4 完成后做，确保所有"长尾文件"在新规则下重新审一遍。

| Phase | 工作量 | 风险等级 | 建议节奏 |
|---|---|---|---|
| Phase 1 | 2-3 天 | 🟢 低（机械替换 + 小心删兜底） | 单独一周内做完，每天 commit + R-VERIFY-01 |

- 每个 Phase 完成后必须按 R-VERIFY-01 自测：`read_lints` → `Tools/godot.bat restart` → `godot-mcp` 端到端
- 每个 Phase 收尾时同步更新本 Roadmap 与重构经验文档
- **极不建议跨 Phase 同时改**：会让冲突难定位

## 五、与 M8/M9 节奏的协调建议

Dolphin 二期开发计划当前节奏（参考 `Plans/二期开发计划.md`）：

- **M8 已完成**：D2.E（GAS 框架、属性、Buff、伤害管线、格挡、能量）
