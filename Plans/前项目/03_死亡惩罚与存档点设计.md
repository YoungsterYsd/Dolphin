## 1. 主理人决策原文

> *"回到存档点（初始点或者上一个关卡存档点）开始游戏。把状态（如背包、货币、本局击杀数量、期间获得的强化等）恢复到该存档点的状态。"*
> —— 主理人 2026-01 第四轮答复

**关键词解析**：
- "存档点"：明确是**点状**（不是连续自动）
- "初始点或上一个关卡存档点"：存档点有**层级**（初始点 + 关卡中的存档点）
- "状态恢复到该存档点"：**完整状态快照回滚**，包括背包/货币/击杀数/强化
- **死亡 ≠ 清档**：死亡不等于"这一局结束"，而是"回到快照"

## 2. 设计定位与风险警示

### 2.1 这还算"肉鸽"吗？

**诚实答案：严格来说，这已经不是传统 Roguelike / Roguelite**。

传统肉鸽的两大核心被削弱：

| 肉鸽核心 | 传统形态（Hades/挺进地牢/死亡细胞）| 本作 v3 形态 | 削弱程度 |
|---|---|---|---|
| 永久死亡（Permadeath）| 死 = 本局全部进度清零，从头开始 | 死 = 回最近存档点（1~3 个房间前）| 🔴 **核心削弱** |
| 每局重建 Build | 每局 Boon/强化全不同，被迫体验新组合 | **同一存档点反复尝试** → Build 在"存档点之间"是固定的 | 🟡 部分削弱 |
| 随机性惩罚 | 抽到烂 Boon = 承担后果 | 不喜欢可死了回档重刷（若存档点前还能抽）| 🟡 部分削弱 |

### 2.2 同类游戏对照 —— 主理人方案最接近哪个？

| 游戏 | 死亡惩罚 | 与本作 v3 相似度 |
|---|---|---|
| **Hades（哈迪斯）** | 回冥府，局内全清，保留 meta 进度（暗黑之暗、镜子升级）| 🔴 完全不同 |
| **挺进地牢** | 回 Breach，局内全清，保留部分解锁 | 🔴 完全不同 |
| **死亡细胞** | 回 Prisoners' Quarters，局内全清，保留永久符文/图纸 | 🔴 完全不同 |
| **暗黑破坏神 II 硬核模式** | 角色永删 | 🔴 完全不同 |
| **暗黑破坏神 III/IV 普通模式** | 回城扣耐久、保留一切 | 🟡 有点像（但无存档点概念）；**v1.2 账号结构高度相似（多角色、角色独立仓库、跨角色共享设置）** |
| **空洞骑士** | 回最近长椅（Bench），保留永久进度，**掉落魂需回死亡点捡**（暗黑式身后物）| 🟢 **非常相似** |
| **魂系（黑魂/艾尔登法环）** | 回最近篝火，地图重置，掉落灵魂需捡 | 🟢 **最相似** |
| **星露谷物语 / 其它农场** | 死亡回家，扣一点金币 | 🟡 友好型 |

**结论**：主理人的方案 = **"魂系篝火 + 空洞骑士长椅"范式**，与任何一款肉鸽都不一样。应该把游戏**重新定位为"带肉鸽元素的动作冒险"**，而不是"肉鸽"。

**v1.2 补充：账号结构接近暗黑**。本轮决策拍板"多角色 + 多存档槽 + 武器仓库 + 自动存档"后，账号层结构完全向 **暗黑 3/4 / POE / 最后纪元** 看齐：
- **账号级全局设置**（画质 / 键位 / 音量）跨所有角色共享
- **角色级独立 Meta**（等级 / 属性点 / 仓库 / 已解锁副本 / 剧情进度）互相隔离
- **角色内 Run 档**（本局进度）为存档点快照 + 自动存档槽并列管理
- 删除角色允许但二次确认（与暗黑一致）

### 2.3 这个决策带来的体验变化

#### ✅ 好处

| 维度 | 变化 | 影响 |
|---|---|---|
| 挫败感 | 极大降低 | 玩家不会因为"玩了 40 分钟被秒"而退游戏 |
| 友好度 | 极大提升 | 新手 / 休闲玩家 / 轻度动作玩家可接受 |
| 反复试错 | 支持 | 玩家可以在 Boss 前反复磨，学习攻击模式 |
| 探索成本 | 降低 | 玩家敢于进未知房间，反正死了回档 |
| 存档点的爽感 | 提升 | 到达存档点 = "安全点" = 情绪释放 |
| 叙事可承载 | 提升 | 存档点可放 NPC、故事碎片、对话选项（回档也不失） |
| 数值/Build 测试 | 方便 | 玩家可以"测试一下新武器再决定要不要" |

#### ❌ 风险

| 维度 | 变化 | 影响 |
|---|---|---|
| **肉鸽爽感** | 🔴 严重削弱 | "绝处逢生"、"一局一命"、"每局都是新冒险"的爽点没了 |
| **死亡的重量** | 🔴 严重削弱 | 死亡变成"读档"，玩家不再恐惧死亡 → 战斗紧张感下降 |
| **随机性的意义** | 🟡 削弱 | 抽到烂 Boon 死一次就可以从存档点重刷 → 随机变可控 |
| **退化成无限读档** | 🔴 高风险 | 魂系通病：玩家遇到难关就"找个安全点存档 → 冲一次 → 死了回来 → 再冲"→ 玩家焦虑、推进慢 |
| **难度曲线崩塌** | 🟡 中风险 | 前面能存档点救命的难度设计，Boss 战无存档点时就显得突兀极难 |
| **重玩价值** | 🔴 严重削弱 | 传统肉鸽"每局不同"的重玩驱动被"推档线性流程"替代 → 玩家通关一次就不玩了 |
| **在线运营空间** | 🟡 削弱 | 肉鸽通常靠"赛季/新词条"延续生命，状态回档式让赛季的重玩驱动变弱 |

### 2.4 策划建议（v1.1 更新：游戏定位正式锁定）

> **v1.1 重大更新**：主理人第五轮定调，游戏定位正式锁定为 **"带肉鸽元素的 RPG"**（此前文档中的"Roguelike"营销口径**作废**）。

**定位变更含义**：

| 维度 | v1 原定位 | **v1.1 官方定位** |
|---|---|---|
| 游戏类型 | Roguelike / 带回档的肉鸽 | **ARPG + 肉鸽元素** |
| 主驱动 | 肉鸽 Run 循环 | **RPG 主线推进 + Meta 成长**，肉鸽元素是"单局内的随机性 + Boon 爽感"|
| 玩家预期 | 死了全清、每局重开 | **死了回存档点 → 继续推进**（魂系篝火预期）|
| 同类对照参考 | Hades / 挺进地牢 / 死亡细胞 | **暗黑破坏神 + 魂系篝火 + 流放之路**（赛季循环）|
| 死亡重量 | 必须很重（肉鸽核心）| **由存档点稀疏度控制**（不必极重）|
| 重玩驱动 | "每局都不一样"| **主线推进 + Meta 解锁 + 单局随机性**|

**策划建议（v1.1 更新）**：

**原则上接受主理人方案**——这是成熟的 ARPG + Roguelite 混合范式，商业上有暗黑 / PoE / 流放之路等大成作品验证可行性。

**必须配合的平衡机制**（由 v1 升级）：

| 推荐平衡机制 | 重要性 | v1.1 调整 | 详见 |
|---|---|---|---|
| **① 存档点适度稀疏 + 房间内强制"推进感"** | 🔴 必做 | 肉鸽纯度要求降低，存档点可以**比 v1 略密**（原 3~5 房间一个 → 可调为 3~4 房间一个）| §4 方案 B + 方案 D |
| **② 局外永久进度（Meta）与局内强化（Boon）严格分离** | 🔴 必做 | 不变，这是 ARPG 铁律 | §3.4 |
| **③ Meta 成长线 + 角色养成 > 肉鸽纯度** | 🔴 必做 | **v1.1 新增**：从"Hades 镜子升级"级别的浅度 Meta → 扩展到"暗黑式角色养成"的深度 Meta（属性点 / 技能树 / 装备持久保留）| 05 文档 §4（肉鸽三层体系）|
| **④ 保留"挑战模式"选项**（死亡全清换高奖励）| 🟡 v1.0+ | 不变 | §4 方案 E |

**理由**：
1. "带肉鸽元素的 RPG"定位下，**肉鸽不再是核心**，RPG 主线推进才是。存档点的友好性反而是优势，不是缺陷。
2. 暗黑 4 / 流放之路 / 最后纪元的成功证明：**Roguelite 元素（赛季、地图随机、词条随机）+ 永久 RPG 养成**是比纯肉鸽更大众的范式。
3. 本作"死亡回档"机制 ≈ 暗黑普通模式 + 魂系篝火，是主流 ARPG 通用语言。
4. 工作量权衡：RPG 定位下关卡量 / 剧情量 > 肉鸽定位下的词条量，资源投入方向应对应调整（具体工作量评估⏸️挂起）。

**不再推荐的表述**：
- ❌ 对外不要用 "Roguelike"（预期不符，会被硬核玩家骂）
- ❌ 不要再与 Hades / 挺进地牢 做硬性对比
- ✅ 对外用 **"带肉鸽元素的动作 RPG"** 或 **"ARPG + Roguelite"**
- ✅ 同类对照用 暗黑 / 流放之路 / 最后纪元 / 空洞骑士

## 3. 存档点机制细则

### 3.1 存档点触发条件

| 选项 | 含义 | 优势 | 劣势 | 参考 |
|---|---|---|---|---|
| a. 只在休息区 | 每关中有固定"休息区房间"，进入即存 | 简单；节点明确 | 存档点密度低，死亡惩罚重；与"友好"目标冲突 | Hades 各区之间的休息站 |
| b. 每进新房间自动存 | 无缝、无感、极友好 | 玩家永不丢进度 | 🔴 退化成"读档速通"；房间内死亡还是要重打房间 | 自动存档类手游 |
| c. 关卡切换时存 | 每章节（Stage）之间一个存档点 | 间隔长，保留紧张感 | 章节内死了损失惨重，劝退新手 | 挺进地牢的章节结构 |
| **d. 玩家主动交互存档点 Actor**（推荐）| 场景中放存档点 Actor，玩家走到跟前按 G 交互存档 | 仪式感强；玩家自主决策；叙事载体 | 玩家可能忘记存 | 魂系篝火、空洞骑士长椅 |
| e. a + d 混合 | 休息区必有存档点 + 关卡内零星放 | 最灵活 | 设计复杂度高 | 神之亵渎 |

#### 推荐：**方案 e（d + a 混合）**

**详细规则**：
- 每个关卡的"休息区房间"**必有**一个存档点（类似 Hades 各区域之间的 Hermes 休息站），玩家走进去自动高亮、按 G 激活
- 关卡内部**不放**额外存档点（保证主流程的紧张感），**每 3~5 个普通战斗房间才会出现 1 个休息区**
- 休息区本身**不强制存档**，玩家进入后要主动走向"存档水晶 / 篝火 / 传送阵"按 G —— 这一"手动存档"动作是仪式感、世界观承载（见 §5.2 复活解释）

### 3.2 ⏸️ 一局内存档点数量（数值部分挂起，结构保留）

> **⏸️ 数值挂起说明**：下面给出的"每 3~5 房间 1 个存档点"和具体关卡布局是**示例占位数值**。v3.1 原则下，**结构（"存档点类型 + 必有休息区 + Boss 前必有"）是本阶段工程要实现的**；**具体数量 / 间隔 / 关卡分布是内容关设计，本阶段挂起**。

根据关卡结构给出 Demo 阶段参考：

```
关卡 1（新手关）：入口 → 房间1 → 房间2 → 房间3 → [存档点：休息区] → 房间4 → [Boss 房]
关卡 2：入口 → 房间1 → 房间2 → 房间3 → [存档点：休息区] → 房间4 → 房间5 → [存档点：休息区] → 房间6 → [Boss 房]
关卡 3+：同上，每 3~5 房间 + Boss 前 1 存档点

初始点（中央枢纽）：永久存在，也是一个存档点
```

| 关卡 | 存档点数量（含休息区）| Boss 前最后存档点距离 |
|---|---|---|
| 关卡 1 | 1 + 初始点 | 1~2 房间 |
| 关卡 2 | 2 | 1~3 房间 |
| 关卡 3+ | 2~3 | 1~3 房间 |

**设计原则**：Boss 战死 = 回到"Boss 前最近存档点"（1~3 房间之前），而不是关卡开头。这是魂系做法，最平衡。

### 3.3 货币 / 物品 / 强化回滚粒度（关键边界）

这是最容易翻车的地方。明确规则：

#### 3.3.1 基本原则：回滚到最近一次"主动存档"的快照

```
时间线示例：
T0: 玩家在存档点 A 手动存档 → 快照 A（背包: 空, 金币: 0, Boon: [], 击杀: 0）
T1: 进房间 1，杀 3 怪 → 击杀数 +3, 金币 +20, 捡到 Boon X
T2: 进房间 2，杀 5 怪 → 击杀数 +8, 金币 +50, 捡到 Boon Y
T3: 到达存档点 B，玩家手动存档 → 快照 B（背包: [药水], 金币: 70, Boon: [X, Y], 击杀: 8）
T4: 进房间 3，花 50 金币买 Boon Z → 金币 20, Boon: [X, Y, Z]
T5: 进房间 4，死亡 → 回到快照 B（金币: 70, Boon: [X, Y], 击杀: 8）

关键：回滚到 B，不是 A（最近手动存档）；Boon Z 消失、50 金币退还、击杀数回滚到 8
```

#### 3.3.2 关键边界（必须明确）

| 边界 | 处理方式 | 理由 |
|---|---|---|
| **商店购买死亡退钱退货** | ✅ 是（因为整个交易被回滚）| 回滚到存档点 = 钱和东西都回去 |
| **已击杀的怪物是否复活** | ✅ 是（存档点之后的怪全部复活，重打）| 魂系标准 |
| **已打开的宝箱是否重置** | ✅ 是（存档点之后的宝箱重新关闭，内容重新生成）| **注意**：若宝箱内容每次随机，刷宝箱成为 cheese 点，见 §7 |
| **已探索的房间小地图** | ⚠️ **不回滚**（QoL）| 玩家已知地图布局，回档不该重打视觉 |
| **房间随机种子** | ⚠️ **回滚**（重新 Roll）| 否则玩家就能"通过回档刷到好房间"|
| **NPC 对话进度** | ⚠️ **回滚**（存档点之后的对话重置）| 否则对话分支系统无意义 |
| **消耗性物品使用** | ✅ 回滚（用过的药水回来）| 与购买一致 |
| **死亡现场"掉落魂"** | ❓ 开放问题（见 §13）| 是否做类魂系"回捡"机制 |

#### 3.3.3 "宝箱 cheese"的修补

若"宝箱内容每次重新随机"，玩家会"死亡 → 回档 → 重开宝箱 → 抽到好的"刷刮刮卡。

**对策（必做）**：
- **同一存档点的同一宝箱，随机种子固定**（保存到存档点快照中的 `RoomRandomSeeds` 字段）
- 玩家死亡回档 → 宝箱内容**与死前完全一致**（同样的奖励抽中）
- 玩家手动存档（新快照）→ 种子**不变**，直到下次存档才重 Roll

**效果**：玩家不能通过"重开宝箱"刷稀有奖励，但保留"换个打法"的灵活。

#### 3.3.4 ⚠️ v1.1 锁定：存档点不锁玩家主动换装（换装 Cheese 承认为可接受）

**决策原文**（主理人第五轮）：
> *"存档点不锁玩家主动更换的换装；不做二次确认弹窗；Cheese 利用'存档→换装试玩→回档'是可接受风险。"*

**规则**：

| 操作 | 存档点附近是否允许 | 本次 Run 的大招池影响 | 存档点快照影响 |
|---|---|---|---|
| 玩家在存档点前主动按 F 切换主副手 | ✅ 允许 | 无（F 不清池）| 切换状态进入下次快照（若玩家再存档）|
| 玩家在存档点附近商店换装 | ✅ 允许 | 被替换武器大招池清空（见 02 文档 F.4.X）| 换装后若存档，新武器/清空后的池值进入快照 |
| 玩家在存档点 UI 主动切换武器（若存档点有装备入口）| ✅ 允许 | 同上 | 同上 |
| 二次确认弹窗 | ❌ **不做** | — | — |
| "刚存档 X 秒内禁换装"冷却 | ❌ **不做** | — | — |
| "距离存档点 X 米内禁换装"拦截 | ❌ **不做** | — | — |

**已承认的 Cheese 链条**（允许玩家自发使用）：
1. 到达存档点 A，按 G 存档
2. 玩家换装尝试武器 X，进入下一房间试用
3. 发现不好用 → 主动触发死亡 / 或自然死亡 → 回档到 A
4. 存档点 A 的 Run Snapshot 恢复：**武器 X 未被替换的原武器回来**、**大招池也按原来恢复**（因为存档快照是在"换装前"打的）

**为什么承认这个 Cheese**：

| 维度 | 策划评估 |
|---|---|
| 玩家获得的收益 | 可低成本试玩不同武器组合 → 降低 Build 试错成本 → 提升 Build 探索乐趣 |
| 策划付出的代价 | 战斗紧张感轻度下降；但 v1.1 游戏定位已改为"带肉鸽元素的 RPG"，紧张感要求本就不高 |
| 工程成本 | **趋近于零**（不拦截即可） |
| 对抗成本 | 高（要做距离判定 / 冷却 / 弹窗 / 历史记录，且玩家总能绕过） |
| **结论** | **承认为可接受风险，不做任何技术拦截** |

**与 02 文档 F.4.X.1 的协同**：
- 02 文档从"战斗 / 装备管线"视角锁定不拦截
- 本节（03 文档 §3.3.4）从"存档 / 回档"视角锁定不拦截
- 两份文档结论一致，工程不需要在两个系统都加 guard

### 3.4 Meta 进度分离（必须铁律）

> **硬规则（非协商）**：局外永久进度 **绝对不回滚**。

| 类别 | 是否回滚 | 存储位置 |
|---|---|---|
| 角色属性（血/蓝/能量）| ✅ 回滚 | 存档点快照 |
| 局内背包 / 局内货币（副本魂 / 本局金币）| ✅ 回滚 | 存档点快照 |
| 局内强化 Boon / 局内词条 | ✅ 回滚 | 存档点快照 |
| 已击杀数 / 本局统计 | ✅ 回滚 | 存档点快照 |
| **永久解锁的武器**（击败 Boss 解锁）| ❌ 不回滚 | 永久存档（SaveGame） |
| **永久属性点 / 镜子升级**（类 Hades 暗黑之暗）| ❌ 不回滚 | 永久存档 |
| **剧情进度 / 已解锁 NPC / 已发现副本** | ❌ 不回滚 | 永久存档 |
| **成就进度** | ❌ 不回滚 | 永久存档 |
| **图鉴 / 怪物百科** | ❌ 不回滚 | 永久存档 |
| **已通关副本统计**（第 N 次通关）| ❌ 不回滚 | 永久存档 |

**技术约束（给工程）**：必须**两套独立的存储系统**：
- `RunSnapshot`：存档点触发时写入，死亡时读取回滚
- `MetaProgression`：独立永久存档，死亡不影响，仅通过"击败 Boss / 完成成就 / 首通解锁"等事件写入

### 3.5 存档槽架构

| 类别 | 数量 | 内容 | 触发 |
|---|---|---|---|
| 自动快照（RunSnapshot）| **1 个**（滚动覆盖）| 当前局进度 | 玩家交互存档点时覆盖 |
| Meta 永久存档 | **1 个**（核心档）| 永久解锁、Meta 货币、设置 | 游戏事件触发 |
| 手动存档槽 | **Demo 不做** | — | 未来可加"多角色档位" |

**Demo 阶段简化**：1 个 Run Snapshot（最近存档点）+ 1 个 Meta 永久档 = 2 个槽位总数。

**不做多快照的理由**：
- 状态回档 + 多槽位 = 玩家会刷"存 A → 冲试一下 → 坏了读 A → 存 B → 再冲"，策略游戏退化
- Demo 阶段目标是"玩家专心推进"，不是"玩家研究存档策略"

**未来可加**："章节回溯"功能 —— 通关一章后可回到章节起点重玩（用 Meta 永久存档里的章节开局快照），**但不能在章节内部多档**。

## 4. 重设计：肉鸽味道如何保留

既然死亡不等于全清，"肉鸽性"需要通过其他途径体现。以下是 5 个备选方案，**推荐组合**：

### 4.1 方案 A：随机性做足

| 机制 | Demo 做法 | 工作量 |
|---|---|---|
| 房间布局随机 | 每局进入关卡，房间顺序和具体房间从池中 Roll | 中 |
| 敌人组合随机 | 每房间从怪物池中 Roll，种类和数量都变 | 中 |
| Boon 选项随机 | 每个 Boon 商人/奖励房给 3 选 1，全池 Roll | 低 |
| 掉落随机 | 怪物掉落物种类、数值浮动 ±20% | 低 |
| 武器位置随机 | 武器商人的库存每次不同 | 低 |
| Boss 变种 | 同一 Boss 有 2~3 套技能组合随机 | 高 |

**结论**：即便死亡不清进度，**每次进入关卡都是新关卡**，玩家每局体验仍然不同。

### 4.2 方案 B：存档点稀疏化

强化 §3.2 的 3~5 房间才 1 存档点原则。具体数值：

| 阶段 | 存档点间隔 | 理由 |
|---|---|---|
| 关卡 1（新手）| 每 3 房间 1 存档点 | 学习期，密一点 |
| 关卡 2~4（中期）| 每 4~5 房间 1 存档点 | 标准节奏 |
| 关卡 5+（高难）| 每 5~6 房间 1 存档点 | 资深玩家对挫败耐受高 |
| Boss 前 | 最后 1 存档点距离 Boss 房 1~3 房间 | 死 Boss 罚重，但不绝望 |

**设计原则**：存档点密度恰好让玩家"死 1 次损失 15~30 分钟"——足够让玩家慎重，又不至于绝望弃游。

### 4.3 方案 C：存档点 = 交易（高级方案）

参考《空洞骑士 · 丝之歌》早期版本的"坐长椅需消耗资源"设计：

| 机制 | 效果 |
|---|---|
| 每次存档消耗 1 "魂水晶" | 玩家要权衡"存不存"——存 = 安全但花资源；不存 = 推进但有风险 |
| 魂水晶在关卡中稀缺掉落 | 成为肉鸽核心资源之一 |
| 特殊 Boon"永动水晶" | 50 局出一次，使下次存档免费 |

**评价**：
- 🟢 优点：极大保留肉鸽紧张感，"存不存"成为核心决策
- 🔴 缺点：新手劝退高；主理人说的"友好回档"体验被削弱
- **Demo 不推荐**，作为"挑战模式"或 v1.0 后扩展

### 4.4 方案 D：Boss 前强制"最后检查点"

| 机制 | 效果 |
|---|---|
| Boss 房前的最后一个存档点 = 入口 | Boss 房内获得的临时 Boon/金币等**不包含在存档里** |
| Boss 战死 → 回存档点 | 背包货币 Boon 回到"Boss 战前"的值 |
| 但 Boss 本身阶段性攻略进度可保留（例如已打掉的一条命）| ⚠️ **不推荐** → 玩家会卡 bug 刷 Boss 血 |

**Demo 推荐**：Boss 战死 = 完全回最后存档点，Boss 血量重置、房间内临时物品全丢。

**与 02 文档 F.6.1 的协同**：Boss 房不再赠送能量 → 玩家从存档点带来多少能量就打多少。死了回档，能量也回到存档点状态。**链条一致**。

### 4.5 方案 E：极限模式（Hardcore Mode）

| 机制 | 效果 |
|---|---|
| 设置菜单可开"极限模式" | 本局内：死亡 = 全清（传统肉鸽）；存档点失效 |
| 完成极限模式奖励 | 特殊皮肤 / 特殊成就 / 特殊 Meta 货币 |
| 与主模式数据分离 | 极限模式的 Meta 进度独立存储（不污染主流程） |

**推荐**：Demo **不做**（工作量大），**v1.0 后作为付费 DLC 或免费更新**提供。

### 4.6 组合推荐（v1.1 更新：游戏定位改为"带肉鸽元素的 RPG"后的降肉鸽纯度版）

> **v1.1 变更**：因官方口径从"Roguelike"改为"**带肉鸽元素的 RPG**"，肉鸽纯度要求显著降低。组合推荐从"最大化肉鸽感"→ "最大化 ARPG 推进感 + 保留适度肉鸽调味"。

| 方案 | v1 Demo 是否做 | **v1.1 Demo 是否做** | 理由（v1.1）|
|---|---|---|---|
| A 随机性做足 | ✅ 必做 | ✅ **必做（维度可精简）** | 房间顺序随机 + Boon 3 选 1 + 掉落浮动**必做**；敌人组合随机 / Boss 变种 **降级为 P1**（v1.0 做，Demo 可先固定） |
| B 存档点稀疏化 | ✅ 必做（3~5 房间 1 点）| ✅ **必做（可放宽到 3~4 房间 1 点）** | 定位改后友好度 > 紧张感 |
| C 存档点 = 交易 | ❌ 不做 | ❌ **不做** | 与"带肉鸽元素的 RPG"的大众向定位冲突 |
| D Boss 前强制检查点 | ✅ 做 | ✅ **必做** | 不变，这是 ARPG 通用做法 |
| E 极限模式 | ❌ Demo 不做 | ❌ **Demo 不做** | v1.0+ 作为可选模式保留给硬核玩家 |

**v1.1 Demo 最终组合 = A（基础维度）+ B（放宽到 3~4 房间）+ D**

**新增平衡机制（v1.1）**：
- **Meta 成长线从"镜子式浅度"扩展到"ARPG 深度"**（等级、属性点、技能树）→ 详见 05 文档 §4 肉鸽三层体系
- **Build 试错成本降低**（与 §3.3.4 换装 Cheese 承认协同）→ 鼓励玩家探索多套 Build，而不是"每局重 Roll 强迫适应"

**v1.1 定位对比同类游戏**：

| 维度 | v1.1 本作 | 暗黑 4 | 流放之路 | 最后纪元 | Hades |
|---|---|---|---|---|---|
| 主流程 | 关卡推进 + 回存档点 | 地下城 + 赛季 | 地图 + 赛季 | 时间线 + 赛季 | Run 循环 |
| 死亡 | 回存档点 | 回城扣耐久 | 回城损失经验 | 回城 | 回冥府 |
| 肉鸽元素 | 房间 / Boon 随机 | 物品 / 词缀随机 | 地图 / Mod 随机 | 时间线 / 词缀随机 | 本局全随机 |
| Meta 养成 | 等级 + 属性点 + 已解锁武器 | 等级 + 传奇属性 | 等级 + 天赋树 | 等级 + 天赋树 | 镜子升级 |
| 游戏定位 | **带肉鸽元素的 RPG** | ARPG + 赛季 | ARPG + 赛季 | ARPG + 赛季 | Roguelite |
| 本作相似度 | — | 🟢 高 | 🟡 中 | 🟢 高 | 🟡 低（仅调味） |

## 5. 复活流程设计

### 5.1 流程时序

```
[玩家血量归 0]
    ↓
[死亡动画 1.2s]（角色倒地、镜头微推、音效重低频）
    ↓
[黑屏淡出 0.5s + "You Died" 式文案]（世界观替代文案，见 §5.2）
    ↓
[加载存档点快照 - 进度条]（1~3 秒，取决于资产加载）
    ↓
[存档点场景加载 + 角色在存档点复活动画 1.0s]
    ↓
[HUD 恢复 + 世界观短文案弹出]（"乐园将你召回..."）
    ↓
[玩家重新获得控制权]
```

**总时长**：约 4~6 秒。比传统肉鸽"死 → 主城 8~12 秒"短，符合"友好"目标。

### 5.2 复活文案与特效

由于死亡即回档是**非常规设定**，需要**世界观解释**（呼应 `04_世界观与叙事骨架.md` 的无限流主神系统）：

| 时机 | 文案示例（待定终稿）| 视觉 |
|---|---|---|
| 黑屏瞬间 | *"……" → "归来" / "重启" / "复苏"*（选一个专用词，见 04 文档 §3.7）| 黑屏 + 白色细字 |
| 存档点苏醒 | *"乐园的权限将你从死亡之前拉了回来。"* | 金色光粒子聚成人形动画 |
| 首次死亡 | *"你察觉到一丝异样——死亡似乎并非终点。"*（教学提示）| 特殊提示框 |
| 连续死亡 3 次 | *"乐园的耐心正在消磨..."*（叙事暗示）| 画面边缘轻微血色 |

### 5.3 复活选择逻辑

主理人原话提到"初始点或上一个关卡存档点"两种。规则：

| 条件 | 复活到 |
|---|---|
| 玩家从未激活任何存档点（刚开新档）| 初始点（中央枢纽）|
| 玩家激活过存档点 | **最近激活的存档点** |
| 玩家已通关某章节但仍在旧章节死亡 | 最近激活的存档点（即使它在旧章节）|
| 玩家在初始点附近死亡 | 初始点 |

**是否需要玩家手动选择"复活到哪里"**：

| 选项 | 优势 | 劣势 | 推荐 |
|---|---|---|---|
| 自动回最近（默认）| 简单、快速 | 玩家想回初始点没得选 | ✅ **Demo 默认** |
| 每次弹窗选择（最近/初始）| 灵活 | 打断节奏 | ❌ Demo 不做 |
| 死亡菜单可选传送回初始点 | 平衡 | 工程成本略高 | 🟡 v1.0+ 加 |

**Demo 推荐**：死亡自动回最近存档点。初始点可通过"主动在任意存档点按某键传送"回去（仿魂系快速旅行）。

### 5.4 死亡次数记录（成就用）

| 记录项 | 存储位置 | 用途 |
|---|---|---|
| 总死亡次数（Meta）| 永久存档 | 成就（如"受苦专精：死 100 次"）|
| 本局死亡次数 | Run Snapshot | UI 显示、影响本局某些触发 |
| 本章节死亡次数 | Run Snapshot | 3 次以上触发 NPC 关怀对话（叙事彩蛋）|
| 特定 Boss 死亡次数 | 永久存档 | 成就 + 首次击败弹出"你死 N 次"文案 |

**创意机制（可选）**：连续死 5 次在同一 Boss → 弹出"乐园怜悯"选项 = 临时降低 Boss 血量 10%（一次性，有 Meta 记录，成就负面标签"获得过怜悯"）。

**v1.2 UnlockedWeaponDefs 字段说明**：

| 子字段 | 类型 | 含义 |
|---|---|---|

- WeaponInstanceID（唯一 ID，用于 UI / 互动锚点）

- AcquiredSource（获取来源：拾取 / 购买 / 任务奖励）

**仓库内武器的能量规则（v1.2 锁定）**：
- 武器卸下进仓库 → **UltEnergy 归零**（与 §3.4 卸装清空规则一致，仓库 = 卸下的终点）
- 仓库中的武器不累积能量（不在身上，自然不吃能量事件）
- 从仓库装回身上 → 从零开始累积

**仓库容量规则（v1.2 推荐）**：
- **Demo 阶段：无上限**（配置字段 Capacity 留 -1 或极大值如 999）
- **v1.0+ 阶段：再讨论是否加 20 格 / 40 格 / 扩容道具**等玩法
- 无上限理由：避免早期内容不丰富时"容量焦虑"干扰玩家试武器探索

### 6.3 关键技术约束（给工程）

1. **原子写入**：存档点交互 → 必须**事务性写入**（要么全成功要么全失败），不允许"写一半崩溃"
2. **双版本保留**：写新快照前先把旧快照备份为 `.bak` 文件，防止写坏导致回档失败
3. **序列化版本号**：每个 Snapshot 带 schema version 号，未来加字段时老存档可兼容升级
4. **大小限制**：单个 RunSnapshot 目标 < 500KB；**Meta 档（含仓库）单角色 < 2MB**（v1.2 上调，因仓库序列化变大）

### 6.4 多角色 / 多存档槽架构（v1.2 新增）

**决策原文**（主理人第六轮）：
> *"当前版本做多角色多存档槽位。"*

#### 6.4.1 顶层结构

```
Meta 档（物理文件层）
    ├─ GlobalSettings.sav            ← 账号级全局设置（跨角色共享）
    │   ├─ KeyBindings
    │   ├─ AudioSettings
    │   ├─ VideoSettings
    │   ├─ LastPlayedCharacterID     ← 启动默认选中
    │   └─ GlobalAchievements（可选，Demo 不做）
    │
    └─ CharacterProfiles/            ← 一个子目录，每角色一份
        ├─ CharacterID_A.sav         ← 角色 A 的 MetaSaveData
        ├─ CharacterID_A.bak
        ├─ CharacterID_B.sav
        ├─ CharacterID_B.bak
        └─ ...
```

**Meta 档逻辑结构（代码视角）**：
```
MetaRoot:
  ├─ GlobalSettings: GlobalSettingsData
  └─ CharacterProfiles: Map<CharacterID, MetaSaveData>
```

#### 6.4.2 CharacterID 生成规则

| 选项 | 推荐 | 理由 |
|---|---|---|
| a. UUID（全局唯一）| ✅ **推荐** | 防冲突、删除后不复用 ID、云存档友好 |
| b. 自增 ID | ❌ | 删除角色后 ID 复用易混淆 |
| c. 玩家输入名字作 ID | ❌ | 改名会破坏 ID；重名冲突 |

**Demo 锁定**：**UUID v4**（或引擎层支持的等价 GUID）。CharacterID 一旦生成不可变；角色名可独立修改。

#### 6.4.3 每角色独立的 MetaSaveData 字段

| 字段 | 归属 | 备注 |
|---|---|---|
| CharacterID | 自身 | 主键，UUID |
| DisplayName | 自身 | 玩家输入的角色名（可改）|
| CharacterClassID | 自身 | ⏸️ Demo 若仅 1 职业可占位 |
| CreatedAt / LastPlayedAt | 自身 | 时间戳 |
| **角色 Meta 属性** | §4 层 4 | OwnedMetaUpgrades |
| **武器仓库** | §6.2 | WeaponStorage（该角色独占）|
| **已解锁武器定义** | §6.2 | UnlockedWeaponDefs |
| **已解锁副本** | Meta | UnlockedDungeons |
| **已解锁存档点** | Meta | SavePointsUnlocked |
| **已解锁 Boon 图鉴** | Meta | UnlockedBoons |
| **剧情进度** | Meta | StoryFlags |
| **成就进度** | Meta | AchievementProgress（**角色级**，每角色独立）|
| **图鉴** | Meta | EnemyCodex / ItemCodex |
| **统计** | Meta | TotalDeathCount / TotalRunCount / TotalKillCount / BossKillCounts |
| **外观** | Meta | OwnedCosmetics + CurrentCosmeticLoadout |

#### 6.4.4 全局共享字段（账号级，不按角色分）

| 字段 | 理由 |
|---|---|
| **设置**（KeyBindings / Audio / Video）| 玩家账号偏好，跨角色统一 |
| **LastPlayedCharacterID** | 启动游戏默认选中上次的角色 |
| **全局成就**（可选） | Demo 不做；v1.0+ 可加"所有角色累计 X"类成就 |

**明确不放全局**：Meta 货币、图鉴、剧情进度、统计、仓库 —— 都按角色独立（与暗黑 4 一致，防止跨角色互刷资源，见 §11 Cheese 防守）。

#### 6.4.5 每角色 Run 状态附属结构

```
CharacterID_A.sav:
  ├─ MetaSaveData { ... }
  └─ RunState:
      ├─ RunSnapshot         ← 最近存档点快照（§6.1 的字段）
      ├─ RunSnapshot.bak     ← 备份
      └─ AutoSaveSlot        ← 自动存档槽（§6.5）
```

**关键点**：
- 每个角色拥有**独立的 Run 状态**，不共享
- 切换角色 = 切换到目标角色的 RunState
- 上一角色的 Run 状态保留在该角色档中（下次切回来继续）

### 6.5 自动存档架构（v1.2 新增）

**决策原文**（主理人第六轮）：
> *"要做自动存档。"*

#### 6.5.1 存档源分类

本作现有两类"存档源"：

| 存档源 | 触发方 | 写入目标 | 参与死亡回档 | 数据内容 |
|---|---|---|---|---|
| **A. 主动存档（存档点）** | 玩家在存档点按 G | **RunSnapshot**（挂到最近存档点 ID） | ✅ **是**（死亡回档的主路径）| §6.1 完整字段 |
| **B. 自动存档** | 引擎事件 | **AutoSaveSlot**（独立单槽） | ❌ **否**（仅异常保护用）| §6.1 完整字段 |

**铁律**：
- 两者**字段结构完全一致**（都是 §6.1 的 Run 状态）
- 两者**物理上独立文件**，互不覆盖
- 死亡回档**优先读 RunSnapshot**（玩家认知的"安全位"）
- AutoSaveSlot **仅在异常场景读取**（下次启动游戏时 / 崩溃恢复）

#### 6.5.2 自动存档触发点推荐组合（策划锁定）

| 优先级 | 触发点 | 是否做 | 理由 |
|---|---|---|---|
| 🔴 P0 必做 | **退出游戏**（玩家点菜单退出 / 关窗口）| ✅ | 保证下次打开能从退出位继续；暗黑 / PoE 标准做法 |
| 🔴 P0 必做 | **关卡切换**（副本 1 → 副本 2 / Run 结束回枢纽）| ✅ | 大跳时强制快照，防止跨关卡崩溃丢进度 |
| 🟡 P1 推荐 | **进入 Boss 房前一刻**（进 BossRoom 的房间切换触发器）| ✅ | 崩溃恢复能回到"即将打 Boss"状态，不用重走前置房 |
| 🟢 P2 可选 | **每 N 分钟定时**（如 5 分钟）| ❌ Demo 不做 | 与"存档点稀疏化"冲突；容易让玩家失去"存档点仪式感" |
| 🟢 P2 可选 | **进入新房间** | ❌ Demo 不做 | 退化成"自动存档式肉鸽"，破坏"回到最近存档点"的设计 |
| 🔴 P0 必做 | **角色切换前**（玩家在枢纽切到另一个角色）| ✅ | 防止切换时当前角色 Run 进度丢失 |
| 🟡 P1 推荐 | **进入互传 UI 目标点后**（互传到达时）| ✅ | 互传本身不写 RunSnapshot（见 §6.6），但可写 AutoSaveSlot 作为崩溃保护 |

**Demo 锁定触发组合**：
```
退出游戏 + 关卡切换 + Boss 房前 + 角色切换前 + 互传到达后 = 5 个事件点
```

#### 6.5.3 自动存档与存档点快照的优先级

```
玩家死亡：
    ↓
读 Meta.LastActiveCheckpointID → 找到对应 RunSnapshot → 回档
（AutoSaveSlot 完全不参与此路径）

玩家下次启动游戏（上次是异常退出 / 崩溃）：
    ↓
检测 AutoSaveSlot 时间戳 vs RunSnapshot 时间戳
    ├─ 若 AutoSaveSlot 更新 → 提示玩家"检测到异常退出快照，是否恢复？"
    │       ├─ 玩家确认 → 从 AutoSaveSlot 读档
    │       └─ 玩家拒绝 → 从 RunSnapshot 读档（最近存档点）
    └─ 若 RunSnapshot 更新或相等 → 直接从 RunSnapshot 读档

玩家主动点"退出游戏"：
    ↓
写 AutoSaveSlot（覆盖）→ 下次启动默认读 AutoSaveSlot
（"继续游戏"按钮默认指向 AutoSaveSlot，相当于"从退出位继续"）
```

**设计意图**：
- **RunSnapshot = 玩家的"安全位"**，死亡回档专用，稳定可控
- **AutoSaveSlot = 玩家的"上次离开位"**，正常退出继续 / 异常崩溃恢复专用
- 两者职责严格分离，不交叉影响

#### 6.5.4 自动存档槽数量

| 方案 | Demo 是否做 | 理由 |
|---|---|---|
| a. 单槽循环覆盖 | ✅ **Demo 锁定** | 简单；玩家预期"继续游戏 = 上次离开处"；无存档策略负担 |
| b. 滚动 3 槽（最近 3 次自动存档）| ❌ | Demo 复杂度收益不高；玩家不会研究自动存档策略 |
| c. 按触发点分类（每触发点 1 槽）| ❌ | 过度设计 |

**Demo 锁定**：**单槽 AutoSaveSlot**，循环覆盖。

#### 6.5.5 自动存档 UI 反馈

| 触发点 | UI 表现 |
|---|---|
| 退出游戏 | 无反馈（退出瞬间完成）|
| 关卡切换 | 加载画面右下角小字 "已自动保存" |
| Boss 房前 | 进入 BossRoom 瞬间右下角 1s 小字 "已自动保存" |
| 角色切换前 | 角色选择界面 loading 条附字 |
| 互传到达后 | 到达地瞬间右下角 1s 小字 |

**不做**：浮夸的"AUTO SAVE"动画 / 旋转图标。保持极简，不打断玩家节奏。

#### 6.5.6 与换装 Cheese / 存档点互传的协同

| 场景 | 行为 |
|---|---|
| 玩家换装 → 自动存档触发 → 死亡 | 死亡读 **RunSnapshot**（存档点前的武器），**换装前的状态恢复**（原 Cheese 继续成立）|
| 玩家换装 → 自动存档触发 → 正常退出 → 重启"继续游戏" | 读 **AutoSaveSlot**，**换装后的状态恢复**（玩家预期"上次离开位"）|
| 玩家互传 → 到达后自动存档 → 崩溃 | 重启恢复读 AutoSaveSlot → 回到目标点 |

**关键：Cheese 不因自动存档扩大**
- 自动存档不参与死亡回档 → 不能通过"死亡 → 回档 → 找自动存档位置"刷
- 详见 §11 新 Cheese 铁律清单

#### 6.5.7 自动存档的原子性与性能

**约束（给工程）**：
1. **非阻塞写入**：自动存档写入必须异步，不能卡住主线程
2. **写入间隔最小保护**：即使触发事件密集（如连续关卡切换），两次自动存档间隔 ≥ 10 秒（防抖）
3. **写入失败不弹窗**：静默失败 + 日志，避免打扰玩家；下次触发点再补写
4. **.bak 保护**：AutoSaveSlot 写入也需 .bak 备份

## 7. 与现有系统的冲突点

| 系统 | 冲突点 | 对策 |
|---|---|---|
| **成就系统** | "本局杀 100 怪"成就，回档后是否重算？| 成就条件分两类：**单局累计类**用 RunSnapshot 的 CurrentRunKillCount（回滚）；**生涯累计类**用 Meta 的 TotalKillCount（死不回滚，杀过就算）|
| **成就系统** | "不死通关本章"成就 | 检测 RunSnapshot.CurrentRunDeathCount == 0，死亡回档后次数 ≥1 即失效（本次通关机会废） |
| **肉鸽强化系统** | 回档丢 Boon，玩家 Build 重建成本 | 设计原则：**存档点之间**积累的 Boon 要让玩家感觉"值得"，死 1 次不致命（存档点间 Boon 数量应为 2~4 个，不要 10+）|
| **商店系统** | 买东西死了退钱 | ✅ 天然支持（货币与物品都回滚）|
| **商店系统** | 玩家 cheese：存档 → 刷商店 → 死了重刷 | **对策**：同一存档点后的商店库存随机种子固定（见 §3.3.3），死了重进还是同一套库存 |
| **NPC 对话** | 对话选项回滚 | 存档点之后的对话进度回滚；存档点之前的不变 |
| **NPC 对话** | NPC "记得"玩家死过几次 | 用 Meta.TotalDeathCount 做对话条件 → NPC 说"你又来了"等彩蛋 |
| **任务系统** | 任务进度回滚 | 主线任务进度用 Meta 存储（不回滚），支线/局内任务用 RunSnapshot（回滚） |
| **卸装清空能量**（02 文档 F.4.X）| 玩家卸下武器前存档 → 死亡回档 → 武器和池子都回来 | ✅ 天然兼容：存档点快照里 EquippedWeapon + UltEnergy 都记录，回滚时一起恢复 |
| **Boss 战** | 打 Boss 死了回存档点，Boss 血量重置 | 已定：Boss 战完全回滚（见 §4.4）|
| **肉鸽"无限乐园"叙事** | 为什么死了能复活 | 世界观解释：主神系统护体（见 04 文档 §3.2）|

### 11.3 v1.2 新 Cheese 风险评估（多角色 + 仓库 + 存档点回档）

**风险背景**：v1.2 拍板后，账号系统引入"多角色 + 仓库 + 自动存档 + 存档点回档"四大机制组合，需重新审视潜在 Cheese 链条。

#### 11.3.1 Cheese 案例分析

**Case 1：仓库满了后，用"存档 → 玩 Run → 死了回档"能否刷武器？**

- 潜在路径：
  1. 玩家在存档点 A 存档（此时仓库状态 = 状态 S0）
  2. 进入 Run 推进，打 Boss 获得武器 W1，**存入仓库**（仓库状态 = S0 + W1）
  3. 继续推进到 B，再打 Boss 获得 W2 **存入仓库**（仓库 = S0 + W1 + W2）
  4. 玩家死亡 → 回到存档点 A → ?

- **关键问题**：回档后 W1 / W2 还在仓库里吗？

- **铁律判定**：
  - **仓库归 Meta 档**（§6.2 / §6.4）→ **不受 RunSnapshot 回档影响**
  - 玩家获得武器 → 若选择"存入仓库" → **立即触发 Meta 写入**（非 Run 写入）
  - 死亡回档 → RunSnapshot 恢复（包括"当时装备的武器 / 背包 / 货币"），但**仓库的 Meta 写入动作不可回滚**

- **这算 Cheese 吗？**
  - 若"存入仓库"是**主动动作**（玩家在存档点 UI 选"移入仓库"）→ 这是玩家意图转移到 Meta，与"永久存档"规则一致，**不是 Cheese**，是合理设计
  - 若"存入仓库"是**自动发生**（如武器满了自动溢出进仓库）→ **有 Cheese 风险**：玩家一拾就刷到 Meta，然后死了回档重刷同一 Boss
  - **铁律**：仓库写入**必须玩家主动触发**，不能自动溢出；见铁律 #R2

**Case 2：多角色相互刷资源是否可能？**

- 潜在路径：
  1. 角色 A 在初始点有 1000 金币（Meta 货币）
  2. 切换到角色 B
  3. 是否能把角色 A 的金币转给角色 B？
  4. 或：用角色 A 的仓库武器装到角色 B 身上？

- **铁律判定**：
  - Meta 档按 CharacterID 切分（§6.4.1）→ **每角色独立钱包 / 独立仓库 / 独立进度**
  - 没有任何 UI 提供跨角色资源转移
  - 除非以后做"共享储物箱"系统（v1.0+ 可考虑，Demo 不做），否则各角色完全隔离

- **结论**：**当前无 Cheese**，但 v1.0+ 若做共享仓库，需要专门设计（防止"角色 A 倾倒资源给角色 B，再删 A 重建"的刷资源链）

**Case 3：删除角色 + 新建角色能否刷初始资源？**

- 潜在路径：
  1. 玩家新建角色 → 系统赠送 100 金币初始资源
  2. 玩家删除角色 → 100 金币理论上应销毁
  3. 再新建角色 → 再拿 100 金币
  4. 无限循环

- **铁律判定**：
  - 如果初始资源只影响该角色自身档（MetaSaveData）→ **删角色 = 档被删 → 资源随之销毁 → 无 Cheese**
  - 如果初始资源进某个"跨角色共享账户"（Demo 未设计此类概念）→ **有 Cheese**

- **Demo 锁定**：初始资源**只写入新角色自身档**，不影响任何共享数据 → **无 Cheese**，见铁律 #R5

**Case 4：自动存档是否能被用来"记录好运 Run"然后回档刷？**

- 潜在路径：
  1. 玩家进副本 → Boss 房前触发自动存档（AutoSaveSlot 写入状态 X）
  2. 玩家打 Boss 失败 → ?

- **铁律判定**：
  - AutoSaveSlot **不参与死亡回档**（§6.5.3）→ 死了回的是 RunSnapshot（最近存档点）
  - AutoSaveSlot 只在"崩溃恢复 / 正常退出继续"时被读 → 玩家正常流程中**无法主动触发读 AutoSaveSlot**
  - 除非玩家"故意 Kill 进程"伪装崩溃 → 这是作弊行为级别（需要熟悉文件路径 + 任务管理器），不构成游戏内 Cheese

- **结论**：**正常玩法下无 Cheese**，但需在存档文件层做防作弊（见铁律 #R6）

**Case 5：利用换装 + 仓库的"武器状态保值"**

- 潜在路径（v1.1 已承认的换装 Cheese 扩展版）：
  1. 玩家武器 W1 满大招池（UltEnergy = 100）
  2. 在存档点存档 → W1 状态入 RunSnapshot
  3. 玩家用 F 切武器/卸下 W1 → **能量归零**
  4. 玩家把 W1 存入仓库 → ?
  5. 玩家从仓库装回 W1 → W1 的 UltEnergy 还是 0 还是 100？

- **铁律判定**：
  - §6.2 锁定："仓库内武器 UltEnergy 归零"
  - 从仓库装回 → 从 0 累积 → **不能通过"入库-出库"保值大招池**
  - 即使玩家死亡回档 → RunSnapshot 恢复"当时装备的 W1 + 能量 100"，但**仓库状态是 Meta，不受回档影响**
  - 如果玩家存档时 W1 在身上 → 回档后 W1 回身上（能量 100 恢复）
  - 如果玩家存档时 W1 已入库 → 回档后 W1 仍在库里（能量 0）

- **结论**：**无 Cheese**，能量机制与仓库机制通过"入库清零"硬隔离

## 12. 验收标准

> Demo 验证时必须满足：

1. **存档点交互流畅**：走到存档点 → UI 提示 → 按 G → 1.5s 存档动画 → "已存档"反馈。全流程 ≤ 3 秒。
2. **死亡回档流畅**：死亡到重新获得控制权 ≤ 6 秒；期间无卡顿、无黑屏卡死。
3. **状态完全回滚**：死亡回档后验证 5 个关键字段与存档点时完全一致（血量/背包/Boon/金币/击杀数）。
4. **Meta 不受影响**：死亡 10 次后验证 Meta 字段（TotalDeathCount +10，其它解锁/成就不变）。
5. **宝箱种子稳定**：同一 snapshot 内的宝箱无论死多少次开出的内容一致。
6. **Boss 战完全重置**：Boss 战死后，Boss 血量、房间状态、临时物品全部重置。
7. **卸装清空与回档协同**：卸下武器 → 存档 → 继续游戏 → 死亡 → 回档 → 武器池值恢复为卸装时的状态（如果那时还在身上）。
8. **Meta 存档文件大小合理**：单角色 Meta 文件 < 1MB、RunSnapshot < 500KB。
9. **玩家反馈**："死了不痛苦，想再试"（抽样 ≥ 70% 正面）。
10. **无存档损坏**：全流程测试无因存档写入失败导致的数据丢失。

## 13. 开放问题清单

以下问题本次未拍板，供主理人下轮决策：

### Q1：死亡现场"掉落魂"机制是否要做？

**背景**：魂系经典设计——死亡时身上未消耗的货币 / 能量掉落原地，复活后回去捡。失败 2 次永久损失。

| 方案 | 优势 | 劣势 |
|---|---|---|
| a. 做（魂系式）| 增加死亡重量；增加"回收风险"策略 | 与"友好回档"冲突；玩家回收现场会反复死 |
| b. 不做 | 流程简洁；真正友好 | 死亡完全无成本，可能失去重量 |
| c. 半做：掉一半，另一半自动保留 | 中间方案 | — |

**策划倾向**：**Demo 不做**。主理人的"友好"取向与魂系"艰难"取向冲突。v1.0 后可作为挑战模式附加规则。

### Q2：首次死亡是否特殊处理（教学免惩罚）？

| 选项 | 说明 |
|---|---|
| a. 首次死亡给叙事教学 + 正常惩罚 | 教学即死亡体验 |
| b. 教学关卡内死亡不消耗"局内强化"（仅扣分）| 友好度最高 |
| c. 教学关卡无法死亡（血量不会归 0）| 极致温柔，但失真 |

**策划倾向**：**a**。教学关就要让玩家体验一次完整的死亡+回档，建立预期。

### Q3：死亡次数是否递增惩罚？

| 选项 | 说明 |
|---|---|
| a. 不递增（死 N 次都一样）| 主理人默认 |
| b. 连死 3 次后复活时轻微减益（debuff 10%）| 增加紧张感 |
| c. 连死 5 次后提供"逃难模式"（临时降低关卡难度 20%）| 照顾手残 |

**策划倾向**：**Demo 选 a**（不递增）；v1.0 后可根据试玩反馈加 c。

### Q4：是否保留"灵魂模式 / 硬核模式"？

见 §4.5，建议 v1.0+ 作为扩展。

### Q5：存档点是否有多种类型？

| 类型 | 效果 |
|---|---|
| 普通存档点 | 存档 + 回血 |
| 主线存档点 | 存档 + 回血 + 触发主线剧情 |
| Boss 前存档点 | 存档 + 回血 + 回切换池 + 可升级装备 |
| 秘密存档点 | 存档 + 回血 + 开启隐藏 Boon |
| **隐形自动存档触发器（v1.2 新增）** | **不可见、不可交互；仅触发 AutoSaveSlot 写入**（见 §6.5）；玩家无感知 |

**Demo 锁定**：
- 可见存档点只做"普通"类型，v1.0+ 再分化出主线/Boss前/秘密
- **隐形自动存档触发器**作为独立系统实现（§6.5），**不计入"存档点"概念**——玩家看不到、不能交互、不参与死亡回档
- 隐形触发器 ≠ 存档点：存档点是玩家可见可交互的地标 + 死亡回档目标；自动存档触发器只是崩溃保护机制

### Q6：✅ v1.1 锁定 — 存档点互传（从 P1 升级为 Demo 必做）

**v1.1 决策原文**（主理人第五轮）：
> *"支持存档点间互传，本身目标就是带有肉鸽元素的 RPG 游戏。"*

> **升级说明**：v1 版本此项为 P1 建议（"存档点 ↔ 初始点 单向传送"）；**v1.1 升级为 Demo 必做**：支持**存档点 ↔ 存档点 双向互传**（不限于初始点）。

#### Q6.1 锁定规则

| 规则项 | v1.1 锁定 |
|---|---|
| 是否实现 | ✅ **Demo 必做** |
| 传送方向 | **双向互传**（任意已解锁存档点 ↔ 任意已解锁存档点）|
| 入口 | 在存档点按 **G** 交互后，在存档点 UI 中进入 "**快速旅行**" 子页 |
| UI 展示内容 | 所有 `Meta.SavePointsUnlocked` 已解锁存档点列表，按所在副本分组展示（副本名 → 存档点名）|
| 展示字段 | 存档点名 / 所在副本 / 首次解锁时间戳 / 是否为当前所在点 / 是否为初始点 |
| **未解锁存档点** | ❌ **不可传**（必须先自然抵达并激活过才解锁）|
| **战斗状态下** | ❌ **禁用**（战斗状态定义见 02 文档 F.10）|
| **消耗** | 🟢 **免费**（v1.1 推荐）| 
| 传送动画 | 屏幕淡出 → 加载 → 目标存档点淡入（类似死亡复活流程，时长 3~5 秒）|
| 传送后状态 | 玩家在目标存档点复活点出生，血量/能量**不变**（与死亡回档不同，互传不是"读档"）|

#### Q6.2 为什么免费（推荐）

| 维度 | 免费 | 消耗货币 | v1.1 选择 |
|---|---|---|---|
| 工程复杂度 | 低 | 中（要定义货币、消耗逻辑、UI 显示）| ✅ **免费** |
| Demo 体验 | 流畅 | 阻断 | ✅ **免费** |
| 与"带肉鸽元素的 RPG"定位契合度 | 高（RPG 探索友好）| 中 | ✅ **免费** |
| 未来可否加成本 | ✅ 可（增加消耗配置字段）| — | 保留字段 `FastTravelCost` |

**工程约束**：§9 配置表保留 `FastTravelCost_SwitchEnergy` 字段（默认 0，即免费），未来若想加成本只需改配置。

#### Q6.4 与现有系统的联动

| 系统 | 互传的联动 |
|---|---|
| 战斗状态（02 F.10）| 战斗中禁用，UI 按钮灰色 + 提示"战斗中无法传送"|
| RunSnapshot | **互传不触发快照写入**（互传不是"手动存档"，只是物理位置转移）|
| 已探索房间 | 互传到目标存档点所在房间，其他"已探索房间"不受影响（QoL 数据独立）|
| 本局状态 | 血量 / 能量 / 背包 / Boon 全部**不变**（区别于死亡回档）|
| NPC / 商店 | 传送到枢纽可访问枢纽商店；传送到副本存档点可访问该存档点附近的 NPC |
| 叙事 | 传送不触发"死亡复活"式文案；单独的"旅途"式短暂过渡动画 |

#### Q6.5 风险与边界

| 风险 | 等级 | 对策 |
|---|---|---|
| 玩家利用互传跳过难房间 | 🟢 低 | 未探索房间不可传；必须自然抵达并激活才能作为目的地 |
| 玩家传送打断 Boss 战进度 | 🟢 低 | Boss 战战斗状态禁用传送；Boss 房内若没有存档点更是无处可去 |
| 互传 UI 与存档 UI 冲突 | 🟢 低 | 作为存档点 UI 的子页，清晰的标签区分（"存档" / "快速旅行"）|
| Cheese：传送到资源房刷 | 🟡 中 | 与 §3.3.3 宝箱种子固定规则协同 —— 即便传过去，宝箱内容也是上次的 |
| Meta 进度（SavePointsUnlocked）丢失 | 🔴 高 | Meta 必须每次解锁新存档点后立即写入（原子写入 + .bak）|

- 存档点处是否有 NPC？（世界观 NPC 守护存档点）
- 存档点是否可升级（永久强化）？
