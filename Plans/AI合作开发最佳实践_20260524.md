# 与 AI 合作开发功能 · 最佳实践流程

> **生成日期**：2026-05-24
> **来源**：Dolphin 项目 M1–M11 + HUD/对话/任务/关卡/道具/掉落/技能编辑器/HD-2D 等十数个里程碑的实际落地痕迹提炼。
> **适用对象**：项目 owner（用户）+ 主 agent（CodeBuddy / Claude Code 等）+ 子 agent（rule-keeper / code-reviewer 等）。
> **适用场景**：从一句"我想加 XXX"到一份 commit 进 master + 验收闭环 的全过程。
> **本文档不是规则**：是经验沉淀；强约束在 `Plans/全局规则.md`（R-* 规则集）。

---

## 一、流程总图（七步法）

```
① 需求落纸 ───► ② 设计文档 ───► ③ 落地路线（Phase 拆分）
                                              │
                                              ▼
                                    ④ 决策点 followup（用户拍板）
                                              │
                                              ▼
                          ⑤ 逐 Phase 落地 + 单 commit 自测（核心）
                                              │
                                              ▼
                          ⑥ 开发日志追加（每 commit 1 条）
                                              │
                                              ▼
                          ⑦ 里程碑收口（验收 + 归档 + 文档导航更新）
```

**核心节奏**：每个 Phase = 一组紧密相关的小 commit（通常 3~10 个），Phase 完成 → 自测 → 追加日志 → 通知用户 → 进下一个 Phase。

---

## 二、详细步骤

### ① 需求落纸（5–10 分钟）

**用户的事**：用一段话或几句话表达"我想要什么"。**不要求严格格式**，但说清以下 3 点已足够：

```markdown
我想做：<功能一句话>
为什么：<解决什么痛点 / 为什么现在做>
范围：<必须有 / 可以有 / 不要的>
```

> **示例（来自实际项目）**：
> "再补充一个功能，命中反馈，技能命中目标后（怪物打人，人打怪物）支持配置生成特效和音效"
> 这一句话主 agent 就足够开干。

**主 agent 的事**：
1. 复述确认（"我理解你的需求是 …，对吗？"）
2. **先扫码**：用 `code-explorer` 子 agent 或 grep/read_file **核查现状**——已有什么、缺什么、有没有部分实现可以复用。
3. 给出一个简短的回信，回答 4 个问题：
   - **多大工程量**（半天 / 1d / 3d / 1w）
   - **影响哪些已有模块**（避免破坏现有功能）
   - **建议拆几 Phase**
   - **有几个决策点要先拍板**

> **真实案例**：用户说"加战后结算"。主 agent 扫码后回信：
> - 工程量约 2 天（指标 11/12 项已就位，UI 共用 BossClear/DeathScreen）
> - 影响 BOSS 战 MVP（共用 widget），无破坏
> - 建议 4 Phase（数据骨架 / UI / 流程编排 / 评级与闪避指标）
> - 0 个决策点（用户已说清要哪些指标）→ 直接进步骤 ②

### ② 设计文档（30–60 分钟）

**输出物**：`Plans/Dolphin设计/<系统名>设计_YYYYMMDD.md`

**强制章节**（按 Dolphin 项目 24 份设计文档归纳）：

```markdown
# <系统名>设计

> 生成日期 / 范围 / 强依赖 / 现状（已就位 + 待补）

## 一、现状盘点
   1.1 已就位（无需新建）✅  ← 列文件 + 一行说明
   1.2 待补（本次新增）🔴   ← 列要做的

## 二、设计目标 / 核心思路
   - 关键决策列表（备选方案 A/B/C + 推荐 + 理由）

## 三、模块设计
   - 文件清单（新增 / 修改 / 删除，每条标注路径 + 类型）
   - 关键代码示意（伪代码即可，不必能运行）

## 四、配置面（策划填什么 / .tres 字段）
   - 编辑入口（Inspector 直填 / Excel 导入）
   - 验收 Demo（2–3 个具体场景）

## 五、与其他系统联动
   - 列 4–6 个交叉点

## 六、落地路线（Phase 拆分）
   - 每 Phase 时长 + 任务清单 + 验收点

## 七、规则联动（R-DATA-02 / R-EVENT-01 / R-VERIFY-01 ...）

## 八、为什么这样设计（决策记录）
```

**关键经验**：
- ✅ **先扫现状再写设计**——避免"重新发明轮子"。Dolphin 项目"命中反馈配置化"设计文档直接发现 Cue 后端管线已就位 90%，工期从估计的 3d 砍到 1d。
- ✅ **包含"为什么这样设计"段**——决策半年后回看不会忘记。
- ✅ **关键架构决策列 followup 表**——A/B/C 三选一，每条说明优缺点，由用户最终拍板。
- ❌ **不要拍脑袋写假设**：未确认的字段名 / 阈值用 `<TBD>` 占位，后续步骤 ④ 时再补。

### ③ 落地路线（10–30 分钟）

**输出物**：`Plans/Dolphin设计/<系统名>落地路线.md`（小系统可与设计文档合并；大系统分开）。

**必备元素**：
- **Phase 0 = 前置基建**（EventBus 信号 / Resource 类骨架 / 配置文件占位 / 命名空间扩展）
- **Phase 1 ~ N = 业务实现**（按依赖排序，从底层往上）
- **Phase 末 = 自测 + Demo 数据**

**Phase 拆分原则**：
| 类型 | 单 Phase 时长 | 单 Phase 内 commit 数 | 验收点 |
|---|---|---|---|
| 前置基建 | 0.2–0.5d | 3–6 | lint 0 错 + 资源能加载 |
| 业务实现 | 0.5–1d | 5–10 | 端到端单链路跑通 |
| Demo 数据 | 0.2d | 2–3 | 演示场景能跑 |
| 自测 | 0.1–0.2d | 0（仅日志） | log 关键证据 + 视觉验收 |

> **真实节奏**（关卡切换升级 M11，~1 小时完成）：Phase 0 信号 → Phase 1 LoadingScreen widget → Phase 2 LevelManager 升级 → Phase 3 LevelTransitionArea → Phase 4 Demo 数据 → Phase 5 自测；每 Phase 平均 10–15 分钟，commit 数 1–3 个。

### ④ 决策点 followup（用户拍板，5–15 分钟）

**主 agent 的事**：把设计文档中所有 `<TBD>` 整理成一份 followup 清单，**每条 3 个备选**：

```markdown
## Q1 · <决策点名>（3 选 1）
A. <方案 A> —— 优：... 缺：...
B. <方案 B> —— 优：... 缺：...（推荐）
C. <方案 C> —— 优：... 缺：...

## Q2 · ...
```

**用户的事**：逐条选 ABC（"全 B"也行，主 agent 把推荐选项标清楚就好）。

**关键经验**：
- ✅ **决策点尽量批量提**：一次 5–8 个 followup，避免来回拉扯。
- ✅ **推荐选项必须标清楚**：用户不愿读详细分析时直接采纳推荐即可（实际 80% 决策走推荐）。
- ✅ **决策落到设计文档「关键架构决策」段**，附用户确认日期。
- ❌ **不要每写一段代码问一次**：那是开发期 R-DATA-02 询问话术（见步骤 ⑤）。

### ⑤ 逐 Phase 落地 + 单 commit 自测（核心，占 70% 时间）

#### 5.1 Phase 内迭代节奏

每个 commit 走 R-VERIFY-01 强制流程（**4 步缺一不可**）：

```
1. write_to_file / replace_in_file  ← 写代码
2. read_lints                        ← 静态校验，0 错才能往下
3. Tools/godot.bat restart           ← 重启 Godot 刷脚本缓存（class_name/Autoload/.tres 必做）
4. MCP 自测                          ← 启动 / 运行 / 提取 log
   - get_editor_logs：确认无 SCRIPT ERROR / Parse Error
   - run_project + 读 log 文件：确认 runtime ready 信号到位
   - get_scene_tree：必要时检查节点树
```

**4 个结果分类**：
| 结果 | 处理 |
|---|---|
| ✅ MCP 跑通 | 日志填「✅ 通过」+ 关键 log 片段，**不打扰用户** |
| ⚠️ MCP 跑不了的视觉/手感 | **显式呼叫用户**："请帮我手测以下 N 项：[具体步骤]" |
| 🔴 lint 出错 | 立刻修，不进下一 commit |
| 🔴 runtime 报错 | 进 debug 子流程（详见 §三 踩坑库） |

#### 5.2 R-DATA-02 询问话术（开发期硬编码询问）

写代码遇到"可能要调"的数值时，**不要擅自硬编码**，按规则 R-DATA-02 模板询问：

> "字段 X 在 `<文件:行号>` 当前硬编码为 Y。这个值未来很可能要调（手感/平衡/美术），建议固化为 `Data/Config/<XxxConfig>.tres` 的 `<field_name>` 字段，由 ConfigCenter 提供 API。是否固化？"

用户回 "是" → 抽 .tres；回 "不用，先硬编码" → 加 TODO 注释 + 继续。**不要默默选其一**。

#### 5.3 commit 粒度建议

**推荐每 commit ≤ 3 个文件 + 单一逻辑变更**：
- ✅ "新增 CombatStats.gd Resource + 字段定义"（1 commit）
- ✅ "CombatStatsRecorder 订阅 EventBus.damage_dealt_v3 累计"（1 commit）
- ❌ "实现整个战后结算系统"（太大，回滚成本高）

**例外**：纯文档批量调整 / 资源 .tres 批量编辑 可以一 commit 多文件。

#### 5.4 错误处理哲学（R-CODE-01）

**崩比静默更好**。Dolphin 项目的硬规则：
- 配置数据缺失 → `assert(cond, msg)` 直接崩
- 必备组件缺失 → `assert` 崩
- API 防御 `if has_method(...)` 都删，让缺失立刻爆出来
- 资源兜底创建（"找不到就 new 一个默认的"）→ 一律删

> **典型反模式**（实际踩过的坑）：
> ```gdscript
> # ❌ 错误写法：找不到默认 attribute_set 就 new 一个 → 永远不会崩，但属性全 0
> if not _attribute_sets.has(set_class):
>     _attribute_sets[set_class] = set_class.new()
>
> # ✅ 正确写法：调用方必须显式声明
> assert(_attribute_sets.has(set_class), "AttributeSet %s not registered" % set_class)
> ```

### ⑥ 开发日志追加（每 commit 1 条，2–5 分钟）

**输出物**：`Plans/Dolphin设计/<系统名>开发日志.md`（持续追加，不分版本）

**单 commit 条目模板**：

```markdown
| 日期 | 阶段 | 改动摘要 |
|---|---|---|
| YYYY-MM-DD | Phase X | 一句话改动；MCP 关键证据 1–2 条；遇到的坑 + 解法（如有）；lint 0 错。|
```

**进度看板**（在日志顶部，每 Phase 完成更新）：

```markdown
| 阶段 | 状态 | Todo 完成 | 验收完成 | 备注 |
|---|---|---|---|---|
| Phase 0 · 前置基建 | 🟢 通过 | 6/6 | 6/6 | 全过 |
| Phase 1 · 业务实现 | 🟡 进行中 | 4/10 | — | T5 卡在 InputContext 优先级 |
```

**关键经验**：
- ✅ **每天结束追加**（不是每周一次），确保细节不丢失。
- ✅ **踩坑必记**：哪怕只是"F8 与 Godot 编辑器 Stop Project 冲突，改 F10 后正常"也要记。
- ✅ **关键证据用日志片段**：runtime log 关键行 / lint 通过截图 / MCP 节点树片段。

### ⑦ 里程碑收口（30 分钟）

**触发条件**：所有 Phase 完成 + 验收通过。

**主 agent 的事**：
1. **更新进度看板**：所有 Phase → 🟢 通过
2. **更新顶层 4 份索引**（如果系统级）：
   - `Plans/项目现状总览_<日期>.md`：把模块加到清单
   - `Plans/已规划未开发清单_<日期>.md`：把项移除（或标 ✅）
   - `Plans/文档导航_<日期>.md`：白名单加新设计/日志条目
   - `Plans/开发计划.md` / `二期/三期`：里程碑状态 → ✅
3. **可选：触发 rule-keeper 扫描**（用户显式说"跑一下规则检查"）
4. **可选：归档过期文档**（参考 `Plans/_Archive/README.md` 规约）

**用户的事**：
1. 视觉/手感最终验收
2. 打 git tag（如 `v0.6-post-stats`）作为下一阶段回退点
3. 决定下一个里程碑

## 三、加速器：常用工具 / 子 agent / 命令

### 3.1 主 agent 必带工具

| 工具 | 用途 | 触发时机 |
|---|---|---|
| `read_file` | 读取已有文件 | 编码前必读上下文 |
| `replace_in_file` | 精准替换（推荐） | 已存在文件改动 |
| `write_to_file` | 整文件覆盖（仅新建） | 新建文件 / 大改 |
| `read_lints` | 静态校验 | 每 commit 后必跑 |
| `execute_command` | 跑 Tools/godot.bat / git mv / Select-String 等 | 重启 / 文档归档 / 简单脚本 |

### 3.2 子 agent（按需派发）

| 子 agent | 适用场景 | 派发时机 |
|---|---|---|
| `code-explorer` | 跨多文件 / 大目录探查 | 步骤 ① 现状扫描 / 步骤 ② 设计前盘点 |
| `code-reviewer-ue5`（项目内对应 godot-rpg-rule-keeper） | 规则合规扫描 | **仅用户显式触发**："跑规则检查" / "rule-keeper" |
| 其他领域专家（gas-combat-expert / rpg-ui-expert 等） | 复杂细分领域决策 | 主 agent 自感能力不足时主动派发 |

> **规约**：子 agent 派发前要写明任务边界（"只读探查" vs "可写代码"），避免越权。

### 3.3 Dolphin 项目专用命令

```powershell
# 重启 Godot 编辑器（R-VERIFY-01 必备）
Tools/godot.bat restart

# 命令行运行项目，捕获 stdout 到文件（最稳的 runtime 验证路径）
Start-Process 'D:\Godot\CompileResult\Godot_v4.6.2-stable_win64.exe' --path d:\Demos\Godot\Dolphin -RedirectStandardOutput out.txt -PassThru
Start-Sleep 5
Stop-Process Force

# 读 runtime log 文件（启用了 file_logging 后自动落到 user data 目录）
Get-Content "$env:APPDATA\Godot\app_userdata\Dolphin\logs\godot.log" -Tail 100
```

### 3.4 godot-mcp 工具集（HTTP 9180）

| 工具 | 主要用途 | 注意事项 |
|---|---|---|
| `get_editor_logs` | 抓启动 / 编辑期日志 | runtime log 常返回空，要用 `source=editor_panel` |
| `execute_editor_script` / `execute_script` | 编辑器进程内跑脚本 | **跑不到 runtime 节点树**（编辑器进程独立） |
| `run_project` / `stop_project` | 启动 / 停止游戏 | Vibe-Coding 模式偶发只 bootstrap autoload，特征：log ≈ 3198B，识别即换路径 |
| `get_scene_tree` | 查看节点树 | 需要游戏跑起来 |
| `set_script` / `set_node_property` | 编辑器内改场景 | 必要时用 |

> **黄金路径**（runtime 行为验证最稳法）：
> 1. 在 project.godot 启用 `application/run/log/file_logging=true`（已开）
> 2. 命令行 `Start-Process` 启动游戏 + 读 log 文件
> 3. 比 MCP 的 run_project 更可靠

## 四、踩坑库（项目实战沉淀）

> 所有踩坑都已沉淀到 `Plans/全局规则.md` 的 R-* 规则集。这里只列**最容易踩**的 6 个。

### 4.1 EventBus 信号订阅必须 named method（R-EVENT-02，2026-05-24 当天踩坑）

```gdscript
# ❌ 禁止：lambda 在节点 free 后不会自动断开，下次 emit 时 capture freed object
EventBus.attribute_changed.connect(func(o,n,old,new): self._update(o,new))

# ✅ 必须：named method 自动跟随 Object 生命周期
func _on_attribute_changed(o:Node, n:StringName, old:float, new:float) -> void:
    if not is_instance_valid(self): return  # 双重防御
    _update(o, new)
EventBus.attribute_changed.connect(_on_attribute_changed)
```

### 4.2 Autoload 不能加同名 class_name（R-ARCH-03）

`class_name ConfigCenter extends Node` + 同名 Autoload → 全项目 Parse Error
**解法**：Autoload 的 .gd 删 class_name，业务侧直接 `ConfigCenter.get_xxx()` 使用。

### 4.3 跨模块状态变更走 EventBus（R-ARCH-04）

ASC 不要 `get_parent().get_node_or_null(^"BlockComponent").stop_block()` —— 改 emit `EventBus.block_broken`，BlockComponent 自己 connect。

### 4.4 改完 @tool 脚本必须重启编辑器（R-VERIFY-01）

Godot 4.6 在启动后新增 class_name / Autoload / .tres 不会自动刷新。
**解法**：`Tools/godot.bat restart`，每次 commit 必做。

### 4.5 Godot F5–F8 是编辑器内置快捷键

`HUDDebugCheats` 用 F8 → 运行时按下立刻 Stop Project（编辑器优先级更高）。
**解法**：避开 F5/F6/F7/F8/F11；用 F1/F2/F9/F10/F12 + Shift 组合。

### 4.6 .tres 引用不存在资源会让整场景子树静默不实例化

删 .tres 后没扫 .tscn ext_resource → 场景子树整体不 _ready，Player 都跑不起来。
**解法**：`Select-String -Path Scenes\*.tscn -Pattern "已删除文件路径"` 全扫一遍。

## 五、与"传统手工开发"的差异点

| 维度 | 传统开发 | AI 合作开发（Dolphin 模式） |
|---|---|---|
| 设计文档 | 写完一次后基本不更新 | 设计 → 落地 → 日志**三件套联动**，开发日志逐 commit 追加 |
| 决策粒度 | 重要决策开会，杂事自行处理 | **R-DATA-02 询问话术**让"未来要调的值"变得显式 |
| 代码评审 | 全功能完成后批量 review | 每 commit lint + 每 Phase MCP 自测，**问题左移** |
| 验收 | 最后跑一次端到端 | R-VERIFY-01 强制每 commit 自测，最终验收无突发 bug |
| 重构 | 等问题积累到一定程度集中重构 | SOLID 审核分批次（Refactor/SOLID审核_批次1–5），与新功能并行 |
| 文档归档 | 旧文档堆积 / 找不到当前版 | `_Archive/` + `文档导航` + `项目现状总览` 三层索引 |
| 上下文管理 | 全在脑子里 / 散落 | `项目现状总览` + `已规划未开发清单` + 各系统开发日志 = 永久外脑 |

## 六、效率参考（实际数据）

> 来自 Dolphin 项目 M11 的实际工期（用户 + 主 agent 配合）

| 系统 | 设计 | 落地 | 自测 + 日志 | 总计 | 文件数 |
|---|---|---|---|---|---|
| 关卡切换升级（M11） | 15min | 45min | 10min | **~1h** | 8 |
| 任务系统（M11） | 30min | 90min | 15min | **~2h** | 12 |
| 对话系统（M11） | 60min | 4h | 30min | **~5.5h** | 19 |
| HUD 13 widget（M11） | 90min | 8h | 60min | **~10h** | 47+21 |
| 道具 Fragment（M11） | 90min | 12h | 60min | **~14h** | 19 |

**经验值**：
- **小功能（1 Phase, 单文件级）**：~30 分钟
- **中功能（3–5 Phase, 跨模块）**：1–2 天
- **大功能（5–10 Phase, 含 UI）**：3–7 天
- **设计文档/落地路线占总时间的 10–15%**——这是性价比最高的投入。

## 七、避坑清单（给用户的）

### 7.1 ✅ 推荐做法
- **一次提一个完整需求**："加战后结算 + DPS/受击/格挡/闪避指标" 比 "加结算" 更省时间
- **批量回 followup**："全 B" / "1B 2A 3B" 一次回完，避免长尾
- **明确"不要的"**："这次不需要评级 / 这次不动美术资源" —— 让主 agent 在落地时少走弯路
- **看到日志反馈"⚠️ 需手测"时立即跑测**：不要积压
- **里程碑结束打 git tag**：作为回退点

### 7.2 ❌ 反模式
- "你看着办" → 大量假设走偏 → 返工成本高
- 一次性下达 5 个不相关需求 → 上下文混乱
- 跳过 R-VERIFY-01 直接合并 → bug 积累到验收期才爆
- 不读开发日志直接拍下一个需求 → 主 agent 重复扫码
- 频繁要求"跑规则检查"作为日常动作（项目已禁用 T1–T4，仅 T5 用户显式触发）

### 7.3 主 agent 的禁忌（自我约束）
- ❌ 主动派 rule-keeper（违反 T5 唯一启用规则）
- ❌ 擅自硬编码可调值（违反 R-DATA-02）
- ❌ Lambda 订阅 EventBus（违反 R-EVENT-02）
- ❌ Autoload 加同名 class_name（违反 R-ARCH-03）
- ❌ ASC 反向调 Component 方法（违反 R-ARCH-04）
- ❌ 兜底创建资源 / `if has_method` 防御（违反 R-CODE-01）
- ❌ 跳过 read_lints / Tools/godot.bat restart / MCP 自测（违反 R-VERIFY-01）
